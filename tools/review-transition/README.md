# ReviewTransition-30

The downstream review-cache boundary is specified independently in
[`REVIEW-CONTEXT-CONTRACT.md`](REVIEW-CONTEXT-CONTRACT.md). Its strict Draft 2020-12 schemas bind the
review context, reviewer-visible input projection, completion manifest, signed prior receipt, and
four-state selected review input without allowing four-way replay to authorize automatic reuse.
The native `review-cache-context`, `review-cache`, and `review-cache-receipt` commands provide the
builder, preflight, and postflight stages; a zero exit code alone never becomes a reusable receipt.

The ReviewTransition-30 selector turns the frozen Review Churn Census v1 artifacts into a
deterministic, auditable set of 30 reviewer transitions. One transition identifies a completed
review checkpoint and the later merged head of the same pull request when the two commit OIDs
differ. The selector itself does not fetch source, run StrataDiff, or score a result. The separate
evaluation CLI observes provider metadata, materializes offline Git inputs, derives an independent
policy oracle, and performs reproducibility replays.

This is a **post-hoc diagnostic sample** drawn from already observed checkpoint-drift cases. It is
deliberately useful for testing the transition workflow and deliberately unsuitable for estimating
prevalence. The Review Churn Census remains the source for frequency estimates over its fixed
panel.

## Claim boundary

A successfully selected and verified plan supports this narrow statement:

> Given the exact bound Census artifacts, policy bytes, seed, and requested count, the tool
> deterministically selected one eligible reviewer transition per pull request and recorded the
> complete reviewer-pair eligibility frame used to make that choice.

For an eligible row, the local frozen evidence establishes all of the following:

- the Census manifest has a latest completed checkpoint;
- the checkpoint and final-head OIDs are distinct 40-character lowercase SHA-1 identifiers;
- the checkpoint review ID joins uniquely to the corresponding captured review;
- that captured review is a GitHub `User` review whose pseudonymous `actor_key` equals the
  manifest `reviewer_key`, and whose commit OID equals the checkpoint OID; and
- the repository's SPDX identifier observed on 2026-09-06 is in the frozen allowlist.

This establishes artifact consistency and selection provenance, not the truth or meaning of the
underlying code change. In particular, it does not establish that either commit will remain
fetchable, that every file is covered by the repository-level license, that redistribution is
lawful, that the transition represents wasted work, or that a product result is correct. A later
materializer must pin and verify fetched Git objects independently.

## Commands

Run from the repository root with Python 3. The default inputs are the four frozen files under
`benchmarks/review-churn-census-v1/` and
[`license-policy-v1.json`](license-policy-v1.json). The default seed is the already frozen
`sampling-plan.json` `selection.seed_hex`; it is not newly generated by this tool.

Select the standard 30-case cohort:

```console
python3 -B tools/review-transition/review_transition.py select \
  --count 30 \
  --output /tmp/review-transition-30.json
```

Every input and the seed can be supplied explicitly when reproducing the plan from relocated
artifacts:

```console
python3 -B tools/review-transition/review_transition.py select \
  --sampling-plan benchmarks/review-churn-census-v1/sampling-plan.json \
  --sample benchmarks/review-churn-census-v1/sample.json \
  --capture benchmarks/review-churn-census-v1/capture.json \
  --manifest benchmarks/review-churn-census-v1/manifest.json \
  --license-policy tools/review-transition/license-policy-v1.json \
  --seed-hex <64-lowercase-hex-characters> \
  --count 30 \
  --output /tmp/review-transition-30.json
```

Verify a saved plan against its bound local inputs:

```console
python3 -B tools/review-transition/review_transition.py verify \
  --plan /tmp/review-transition-30.json
```

`verify` rejects duplicate JSON keys and non-canonical or structurally altered output. It reads the
bound count and seed, regenerates the complete plan from the source artifacts, and requires the
result to match structurally and byte for byte. This detects changes to selected identities, OIDs,
digests, dispositions, ordering, counts, or source bindings; it does not authenticate the original
publisher or prove that provider metadata was historically correct.

Run the offline regression suite with:

```console
python3 -B tools/review-transition/review_transition.py self-test
```

`self-test` exercises selection and tamper detection. It does not contact GitHub and creates no
benchmark or product evidence.

Capture the bounded GitHub PR and Compare metadata into a resumable canonical observation:

```console
GITHUB_TOKEN=... python3 -B tools/review-transition/review_transition_eval.py observe \
  --plan /tmp/review-transition-30.json \
  --output /tmp/review-transition-30-observation.json
```

The token is read only from the environment variable named by `--github-token-env`, which defaults
to `GITHUB_TOKEN`; it is never accepted as a command-line value or written to the artifact. A run
retains every already observed row and retries pending or failed rows. It exits 0 only for a 30/30
observation and exits 2 after safely writing an incomplete, resumable observation.

Verify a complete observation and all of its plan, protocol, request, raw-response-digest, summary,
and route bindings with:

```console
python3 -B tools/review-transition/review_transition_eval.py verify-observation \
  --plan /tmp/review-transition-30.json \
  --observation /tmp/review-transition-30-observation.json
```

This command freezes Q, B, D, and the provider's single merge-base candidate for each comparison.
It does not prove A or C: those require an offline-complete Git materialization and independent
`git merge-base --all` checks. Materialization and verification are exposed below, but no complete
30-case materialization artifact is checked in. Oracle generation and double offline product replay
are also executable engineering paths; partial runs remain explicitly `not_evaluated` and are not
completed ReviewTransition-30 evidence.

The checked-in [provider observation](../../benchmarks/review-transition-30/README.md) completed all
30 cases with 11 `provider_attested_same_base` and 19 `requires_full_ancestry` routes. Its canonical
SHA-256 is `4c2a5e813c905016993e540578c339185cafc8fbc0c73360d9722edca50995b5`.

Materialize complete commit ancestry and the required source closure into remote-free bare
repositories, then verify them offline:

```console
GITHUB_TOKEN=... python3 -B tools/review-transition/review_transition_eval.py materialize \
  --plan /tmp/review-transition-30.json \
  --observation benchmarks/review-transition-30/provider-observation-v1.json \
  --output /tmp/review-transition-30-materialized
python3 -B tools/review-transition/review_transition_eval.py verify-materialization \
  --plan /tmp/review-transition-30.json \
  --observation benchmarks/review-transition-30/provider-observation-v1.json \
  --materialization /tmp/review-transition-30-materialized
```

The fetch has no depth limit and uses `blob:none`; required endpoint blobs are then fetched by exact
OID. Verification requires a non-shallow repository, no configured remote, exact Q/A/B/C/D commit
and tree OIDs, unique A/C merge bases, and every recorded required blob with lazy fetching disabled.
The manifest always retains all 30 frozen cases with `observed`, `materialized`, or `failed` status,
plus an exact summary and `complete` flag. It is updated atomically after each attempted case, so a
later invocation verifies and reuses completed repositories while retrying failed or untouched
cases. A single-case engineering smoke can use repeatable `--case-id` or `--max-cases`; the command
then exits 2 and leaves every other cohort member visibly incomplete. `verify-materialization`
rejects such an artifact unless `--allow-incomplete` is explicit.

When retrying a failure produced by an older manifest writer, preserve its original budget
explicitly instead of overwriting the evidence. For example, after a 120-second acquisition timeout,
retry only that frozen case with:

```console
GITHUB_TOKEN=... python3 -B tools/review-transition/review_transition_eval.py materialize \
  --plan /tmp/review-transition-30.json \
  --observation benchmarks/review-transition-30/provider-observation-v1.json \
  --output /tmp/review-transition-30-materialized \
  --case-id <failed-case-id> \
  --legacy-attempt-timeout-seconds 120 \
  --fetch-timeout-seconds 600
```

The case keeps ordered attempt records with both timeout budgets and the original failure. The
higher retry timeout is a dataset-construction acquisition budget, not a relaxation of product
latency or review behavior; offline product replay uses the same product command and policy for
every evaluated case.

`--max-repository-bytes` is a post-fetch, per-stage object-store guard. It is checked after the
commit fetch and each exact-blob batch, but it is not a network wire-byte limit and must not be
reported as one.

Derive the policy oracle only from the verified offline repositories, then recompute it independently:

```console
python3 -B tools/review-transition/review_transition_eval.py generate-oracle \
  --plan /tmp/review-transition-30.json \
  --observation benchmarks/review-transition-30/provider-observation-v1.json \
  --materialization /tmp/review-transition-30-materialized \
  --output /tmp/review-transition-30-oracle.json
python3 -B tools/review-transition/review_transition_eval.py verify-oracle \
  --plan /tmp/review-transition-30.json \
  --observation benchmarks/review-transition-30/provider-observation-v1.json \
  --materialization /tmp/review-transition-30-materialized \
  --oracle /tmp/review-transition-30-oracle.json
```

The oracle interface has no product-result input. It independently enumerates current identities,
exact and non-interacting four-way carries, needs-review identities, retired checkpoint changes,
non-UTF-8 unresolved retired changes, and A-to-C base-drift obligations. Its canonical artifact is
bound to the exact materialization bytes.

After the oracle is frozen, run and verify two product executions per selected case:

```console
python3 -B tools/review-transition/review_transition_eval.py replay-product \
  --plan /tmp/review-transition-30.json \
  --observation benchmarks/review-transition-30/provider-observation-v1.json \
  --materialization /tmp/review-transition-30-materialized \
  --oracle /tmp/review-transition-30-oracle.json \
  --binary target/release/stratadiff \
  --output /tmp/review-transition-30-replay
python3 -B tools/review-transition/review_transition_eval.py verify-product-replay \
  --plan /tmp/review-transition-30.json \
  --observation benchmarks/review-transition-30/provider-observation-v1.json \
  --materialization /tmp/review-transition-30-materialized \
  --oracle /tmp/review-transition-30-oracle.json \
  --binary target/release/stratadiff \
  --replay /tmp/review-transition-30-replay
```

Each run receives a separately copied, remote-free repository with lazy fetching, replacement refs,
and object alternates disabled. Product JSON is parsed with duplicate-key rejection and rewritten to
canonical bytes before the two reports, review deltas, summaries, and result digests are compared.
`--case-id` and `--max-cases` are available for bounded engineering smoke runs; all unrun cohort rows
remain `not_evaluated`, and a partial replay exits 2.

The default canonical plan is also bound by
[`evaluation-protocol-v1.json`](evaluation-protocol-v1.json). With the current frozen inputs its
canonical bytes have SHA-256
`d0287a0319c7e2dd7298e7a141b00be0dbfc2db8dfd75ac2a42259ceb072fdb9`. The regression suite
requires that digest and the following frame totals: 500 pull requests, 589 reviewer pairs, 55
eligible pairs, 47 distinct eligible pull requests, and 30 selected cases. A selection change must
therefore be an explicit protocol/version change, not a silent test fixture update.

The canonical evaluation protocol is independently pinned by the evaluator at SHA-256
`b804e08ff34d69e4e4d7820abe35d9bb27b82165db6a5f5af3dbd2177c29c194`. Supplying a same-version
protocol with altered truth, failure, measurement, or reproducibility rules is rejected.

## Bound inputs

The selector validates the following raw-byte chain before considering any reviewer pair:

```text
sampling-plan.json
  -> sample.json source_plan.sha256
  -> capture.json source_sample.sha256
  -> manifest.json sampling_plan_sha256, sample_sha256, capture_sha256
```

It also checks each artifact's schema identifier and dataset version, rejects unknown top-level
fields, validates the selection-relevant nested structures, requires the selected pull-request
sets to agree across `sample.json`, `capture.json`, and `manifest.json`, and records the raw SHA-256
of all four inputs and the license policy in the output. Editing JSON whitespace changes a raw-byte
binding even when the parsed value is unchanged.

The output uses schema `stratadiff-review-transition-plan-v1` and dataset version `0.1.0`. It keeps
the complete reviewer-pair frame, not only the 30 winners. Every row has one of these dispositions:

- `selected`;
- `eligible_not_selected`; or
- `excluded`, accompanied by explicit exclusion reasons.

The selected identities include the Census case ID, repository, pull-request node ID and number,
pseudonymous reviewer key, checkpoint review ID/state/OID, final-head OID, observed SPDX ID, and
selection digest. Summary counts must reconcile with the complete frame.

## Deterministic selection

The selector first builds a row for every reviewer pair in the manifest. Eligibility depends only
on the frozen transition facts and license policy described above. Downstream product output,
including any field named `product_result`, is outside the selection domain and cannot affect an
identity or digest.

For each eligible pair, the rank digest is:

```text
SHA-256(
  UTF-8("stratadiff-review-transition-selection-v1")
  || 0x00
  || seed_bytes
  || 0x00
  || UTF-8(case_id)
  || 0x00
  || UTF-8(reviewer_key)
)
```

`seed_bytes` is the 32 bytes decoded from the lowercase 64-hex seed. The NUL separators and UTF-8
encoding are part of the contract.

Eligible pairs are ordered by the unsigned lexicographic order of their 32-byte digest. Within
each pull request only its lowest-digest reviewer survives, so the output contains at most one
transition per PR. Those per-PR winners are globally ordered by the same digest and the first
`--count` rows are selected. If fewer than the requested number of distinct eligible PRs remain,
selection fails; there is no relaxed license rule, repeated PR, or outcome-informed replacement.

## Evaluation readiness

Selection readiness and product-evaluation readiness are different gates. The current artifact has
the frozen reviewer checkpoint B and final head D for all 30 cases, but it does not yet contain the
requested base Q, independently derived merge bases A and C, an offline-complete Git object closure,
an independent per-change oracle, or a normalized product result. Therefore the selector alone
cannot measure false skip, false carry, residue reduction, block rate, latency, bandwidth, or token
savings.

[`evaluation-protocol-v1.json`](evaluation-protocol-v1.json) preregisters the missing contract before
any ReviewTransition-30 product outcome is observed. Its five-snapshot model is:

```text
Q = exact requested base frozen by the materialization manifest
A = unique full-history merge-base(Q, B)
B = frozen completed-review checkpoint
C = unique full-history merge-base(Q, D)
D = frozen final PR head

reviewed checkpoint delta = A..B
current PR delta          = C..D
```

The independent oracle must run without reading StrataDiff output. It must enumerate every current
Git change identity, exact carry, strict non-interacting four-way carry, residue identity, retired
checkpoint change, unresolved retired change, and base-drift obligation. Only after that oracle is
frozen may the evaluator compare the product result. `needs_review_now` remains policy-conformance
ground truth, not a human judgment that a file is important or semantically unsafe.

The first safety gate is zero policy false carries and zero false skips across the unchanged 30-case
cohort. Missing objects, multiple merge bases, incomplete source closure, timeouts, or malformed
output must never enter either numerator as a success and must never trigger outcome-informed case
replacement. Acquisition failures and product blocks have separate rates and denominators.

Reduction must be reported independently for current change identities, text changed lines, and the
exact canonical downstream-review payload bytes. Binary or unavailable line counts are reported,
not converted to zero. Token savings exist only when the exact payload serialization and tokenizer
name, version, and vocabulary digest are pinned. Provider/API time, Git materialization time,
offline analysis time, and Workbench readiness time are separate latency phases. Actual received
wire bytes are bandwidth; pack or object-store size is storage and cannot substitute for it.

This protocol caches **verified review input**, not an AI review verdict. File-local identity is
insufficient for a reviewer whose judgment also depends on imports, generated registries, build
configuration, policy files, or other dynamic repository context. Unless that consumer declares
and hashes its complete input closure together with its implementation/model and configuration,
an empty file-local residue cannot authorize verdict reuse. ReviewTransition-30 does not evaluate
that stronger claim, and its token metric means input-token reduction only. The discussion in
[`alibaba/open-code-review#854`](https://github.com/alibaba/open-code-review/issues/854) makes the
distinction concrete: the same file-diff fingerprint can coexist with changed context that an agent
read elsewhere in the repository.

### Bounded live metadata preflight, 2026-09-06

A read-only, bounded GitHub REST preflight queried the exact 30 selected PRs and two comparisons per
case without fetching source. All 30 PR lookups succeeded, every live head still matched frozen D,
and all 60 comparisons resolved. The relationship strata were:

| Q...B / Q...D status | Cases | Materialization implication |
|---|---:|---|
| `ahead / ahead` | 11 | eligible for the provider-attested same-base path after both merge bases equal Q |
| `diverged / ahead` | 13 | full Git ancestry required |
| `diverged / diverged` | 6 | full Git ancestry required |

This is now a frozen availability observation, not provider-authenticated ancestry truth or a
product result. In particular, the REST Compare API exposes only one merge-base candidate. The 19
diverged cases must fetch enough history to run `git merge-base --all`; zero or multiple best merge
bases fail closed. The next materialization artifact must bind this checked-in observation, retain
all 30 cases without replacement, then materialize and remove every remote before oracle generation
and evaluation.

The final report must preserve this route distribution and separately publish the ancestry-
materialization failure rate over the 19 full-history cases. Exact-object unavailability, timeout or
resource exhaustion, no merge base, and multiple best merge bases are distinct failure strata; none
may be silently folded into an evaluated `full` result or removed from the 30-case cohort.

A first bounded smoke run on `github/gh-stack#147` exercised the same-base path. The initial
metadata-only partial repository occupied 524 KiB and the observed command took about 0.62 seconds,
but its promisor remote remained configured and all 29 current files were `unverified` because their
source blobs were absent. That timing is not a source-complete benchmark.

A follow-up copy hydrated the 52 blobs referenced by the review and delta, removed every remote,
and reran with `GIT_NO_LAZY_FETCH=1`. The product again reported 29 current files, 15 exact carries,
a 14-file residue, and zero unresolved retired changes. An independent raw-diff set cross-check
found 29 checkpoint changes, 29 current changes, a 15-identity intersection, 14 checkpoint-only
identities, and 14 current-only identities. The bounded repository occupied 696 KiB; one unoptimized
developer-build analysis took 7.54 seconds and 74,400 KiB maximum RSS. Twenty-seven files received
source analysis while `go.mod` and `go.sum` remained explicitly unverified because their extensions
have no supported parser. This is still one exploratory case, not a frozen oracle, distribution, or
ReviewTransition-30 performance claim.

A second bounded development smoke run exercised the complete-ancestry route on frozen case
`github/gh-stack#185`. The current `0.5.0` development binary reached a ready Workbench in
`34.142823` seconds with a maximum observed child RSS of `262960` KiB. It reported 24 current
needs-review files, 9 retired checkpoint changes, 7 base-drift entries, and no unresolved retired
change. All 48 resume-source and 14 base-source endpoints returned HTTP 200 with recorded byte
lengths. Eleven resume entries and all seven base entries produced independently verified
structural reports; 13 image or otherwise unsupported resume entries returned the designed 422
detail response while retaining their downloadable source snapshots. SIGINT left no new
`gh-stratadiff-resume-*` directory. This remains one operator-observed smoke run: it does not replace
the 30-case materialization, independent oracle, or two-clean-run evaluation.

## License policy

[`license-policy-v1.json`](license-policy-v1.json) is a frozen observation and selection policy,
not legal advice. Its closed object has exactly these fields:

- `schema`: `stratadiff-review-transition-license-policy-v1`;
- `policy_version`: `1.0.0`;
- `observed_at`: the observation date `2026-09-06`;
- `source`: `github_repository_license_metadata`;
- `allowed_spdx_ids`: the unique, canonically ordered exact allowlist; and
- `repositories`: the ten unique Census repository names and their observed SPDX identifiers,
  canonically ordered by case-insensitive repository name.

The parser rejects missing or additional fields, duplicate keys or array values, malformed names,
an unexpected repository set, policy constants that differ, or non-canonical ordering. Matching is
exact and case-sensitive. The only allowed SPDX identifiers are:

```text
0BSD
Apache-2.0
BSD-2-Clause
BSD-3-Clause
ISC
MIT
```

The frozen observations are:

| Repository | SPDX observed 2026-09-06 | Eligible by policy |
|---|---|---:|
| `dotnet/runtime` | `MIT` | yes |
| `elastic/elasticsearch` | `NOASSERTION` | no |
| `github/gh-stack` | `MIT` | yes |
| `grafana/grafana` | `AGPL-3.0` | no |
| `home-assistant/core` | `Apache-2.0` | yes |
| `kubernetes/kubernetes` | `Apache-2.0` | yes |
| `microsoft/vscode` | `MIT` | yes |
| `PostHog/posthog` | `NOASSERTION` | no |
| `rust-lang/rust` | `Apache-2.0` | yes |
| `vercel/next.js` | `MIT` | yes |

`NOASSERTION` is always excluded; it is not treated as permissive or as a missing value that may
fall back to another rule. `AGPL-3.0`, license expressions, exceptions, missing metadata, and every
other identifier are also outside this v1 allowlist. Metadata changes require an explicit,
versioned policy update and a newly bound plan rather than silently changing an existing cohort.
Repository-level metadata is only a conservative selection gate; downstream users remain
responsible for file-level notices, generated or vendored content, contribution terms, and their
intended use.

## Privacy and unsupported claims

The plan must not contain GitHub login strings or username fields. It uses the Census
`actor-<24 hex>` reviewer keys and retains only the public repository, pull-request, review-node,
and commit identifiers needed to audit a transition. Those public identifiers can still be looked
up and linked back to people, so the artifact is privacy-minimized, not anonymous. Do not use this
format for private repositories or add identity mappings, review prose, comments, email addresses,
tokens, or raw provider responses.

Neither selection nor successful verification supports claims about:

- reviewer time saved, issue recall, false carry, review quality, or merge safety;
- the amount, difficulty, or semantic importance of code changed between the two commits;
- causal effects of Review Resume or any comparison with another tool;
- demand, willingness to pay, market size, or product-market fit; or
- GitHub-wide, open-source-wide, repository-wide, or time-period prevalence.

Those questions require materialization checks, independently specified evaluation metrics, and,
for reviewer outcomes, the separate preregistered human study. ReviewTransition-30 only makes the
input cohort reproducible and inspectable.
